1. Mandatory oral answers

Question: Basics of an HTTP server.
Answer:
An HTTP server listens on one or more sockets, accepts TCP clients, reads HTTP
requests, parses the request line, headers, and optional body, maps the URI to
a configured route, builds an HTTP response with a status line, headers, and
body, then sends it back to the client. For HTTP/1.1 it also handles keep-alive
unless the connection must close.

Question: Which function is used for I/O multiplexing?
Answer:
This project uses poll().

Show:
Run: grep -n "poll(" server.cpp
Expect: poll appears in the main server loop.

Question: How does poll work?
Answer:
poll receives an array of pollfd structures. Each entry contains a file
descriptor and the events we want to watch, such as POLLIN for readable data
or POLLOUT for writable output. poll blocks until at least one descriptor is
ready or until the timeout expires. After it returns, the program checks
revents and performs at most the I/O operation that is ready.

Question: Do you use only one poll, and how do you manage accept/read/write?
Answer:
Yes. The main loop calls poll once over all listening sockets, client sockets,
and CGI pipe descriptors. Listening sockets with POLLIN are accepted. Client
sockets with POLLIN are read with recv. Client sockets with POLLOUT are written
with send. CGI pipes are also handled through the same poll loop.

Show:
Run: grep -n "accept\\|recv\\|send\\|read\\|write\\|pipe\\|poll" server.cpp
Expect: socket/pipe I/O is handled from the poll-driven server code.

Question: Why only one read or write per client per poll?
Answer:
Because after poll reports readiness, the server performs one recv or one send
for that ready descriptor, then returns to the loop. This avoids blocking one
client while serving another and keeps the event loop responsive.

Question: Are read/recv/write/send return values checked?
Answer:
Yes. recv checks negative return for error and zero for closed connection.
send checks positive bytes sent, negative error, and keeps unsent data pending.
CGI pipe read/write also check return values and clean up or finalize on error.

Important evaluation warning:
Do not check errno after read/recv/write/send as the main behavior. The scale
says this is forbidden. The return value must drive the logic.

Question: Does the server read/write file descriptors outside poll?
Answer:
Network sockets and CGI pipes are managed through poll. Normal file reads and
writes for static files/uploads are not sockets and are allowed.

Question: What happens on bad request/unknown method?
Answer:
The parser throws or marks an error response. Unknown methods return 501 Not
Implemented. Bad syntax returns 400. The server must not crash.

Question: What happens on SIGINT/SIGTERM/SIGPIPE?
Answer:
SIGINT and SIGTERM set a global signal flag so the server exits its loop and
closes descriptors. SIGPIPE is ignored so a broken client connection does not
kill the server process.

Show:
Run: grep -n "signal\\|SIGPIPE\\|SIGINT\\|SIGTERM" AppManager.cpp WebservUtils.cpp

3. Configuration features to explain

Current webserv.conf includes:
- one server on port 8080
- host 0.0.0.0
- server_name localhost
- root ./www
- index index.html
- client_max_body_size 1M on the server
- GET-only route /
- GET-only route /directory/ mapped to ./YoupiBanane
- POST-only route /post_body with client_max_body_size 100
- CGI POST route /YoupiBanane/ for .bla using ./cgi_tester

Answer: multiple ports
The parser supports multiple server blocks. Each block can listen on a port.
The server opens one listening socket per unique port and maps clients back to
the selected server configuration.

Answer: multiple hostnames
When more than one server uses the same port, the Host header is used to select
the matching server_name. Test with curl --resolve or with a Host header.

Answer: custom error pages
The config supports error_page. If a matching custom page exists, it is loaded.
Otherwise the server builds a default HTML error page.

Answer: routes
Each location can override root, index, allowed methods, CGI settings,
autoindex, return redirects, and client body limit.

Expect: HTTP/1.1 413 because /post_body limit is 100 bytes.

===========================================================================================
								STATUS CODES
===========================================================================================

200 OK:
Successful GET or CGI response.

201 Created:
Successful upload/write through POST.

204 No Content:
Successful DELETE.

301 Moved Permanently:
Configured redirect.

400 Bad Request:
Malformed request, invalid headers, missing Host.

403 Forbidden:
Invalid path, access denied, cannot write.

404 Not Found:
Requested file/route target does not exist.

405 Method Not Allowed:
Route exists but method is not allowed in allow_methods.

411 Length Required:
POST without Content-Length or Transfer-Encoding.

413 Payload Too Large:
Request body exceeds configured client_max_body_size.

414 URI Too Long:
Request line or URI exceeds parser limit.

500 Internal Server Error:
Unexpected server/CGI setup failure.

501 Not Implemented:
Unknown HTTP method.

505 HTTP Version Not Supported:
HTTP version is not HTTP/1.1.
